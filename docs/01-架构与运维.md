## 二、抓取链路

```
scheduler.check_and_crawl()
   ├─ 取一台可用设备（devices 表里 status='active'）
   ├─ xhs_client._signer(payload)         ← ver=='9.49.1' 走 XhsSigner9491
   ├─ GET /api/sns/v4/note/user/posted     ← 拉该博主笔记列表
   ├─ 合并去重 → notes 表 → notifier 推送
   └─ 把设备状态 / 昵称 / user_id 回写
```

签名材料生成（`device_factory.generate_offline`）：

```
随机机型 → UA(9.49.1/9491803) → gid → mua0(tiny_mua, v2.10.1) → cp(9.49.1/9491803, cpu_abi=armeabi-v7a)
        → platform_info(build=9491803) → shield(纯 Python RC4) → s1(perm8 用真实算法)
        → payload 里写 ver='9.49.1'
```

> ⚠️ **材料版本必须自洽**：UA 的 `Version/x Build/y` ↔ cp 的 `versionName/build` ↔ platform_info 的 `build`
> ↔ mua 头 `v` ↔ cp `cpu_abi` 与 mua `x21`。服务端会校验这些，任一处不一致容易吃 `461`。
> 2026-10-26 之前 UA/cp 是 9.19.2 而 mua 是 2.10.1，就是这个坑，已修。

### 材料校验已经自动化（2026-10-26）

| 时机 | 行为 |
|---|---|
| **生成时**（`generate_offline`） | 末尾自动跑 `verify_material()`，不自洽直接 `raise DeviceFactoryError`，**坏材料进不了库** |
| **存量巡检** | `GET /api/devices/material_audit` 逐台列出 `problems`，空数组 = 合格 |

查的 4 类（都是服务端真的会校验的）：

```
① 必需字段   device_id / did / hmac / key64 / mua0 / cp / platform_info / user_agent
② 版本一致   UA 的 Version+x Build/y  ↔  cp.versionName + cp.build  ↔  platform_info.build
③ mua 版本   ver=9.49.1 → mua 头 v 必须 2.10.1 ；ver=9.19.2 → 2.9.55
④ cpu_abi    ver=9.49.1 时必须是 armeabi-v7a（官方只发 v7a）
```

> 存量设备（payload 里没有 `ver`）只查 ①②，不查 ③④，避免把历史设备误判成坏材料。

## 三、部署

**只传代码，不重建镜像**（重建会连带改运行环境）。

```bash
# 本地工作副本：F:/Workbuddy/xhs-monitor/_loginonly/
# 1) 上传到宿主机 build context（下次 build 也不会回退）
sftp> put _loginonly/app.py /home/ubuntu/xhs-monitor/app.py
# 2) 进容器
sudo -n docker cp /home/ubuntu/xhs-monitor/app.py xhs-monitor:/app/app.py
# 3) 重启
sudo -n docker restart xhs-monitor
# 4) 冒烟
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/api/auth/status
```

**两处都要传**：宿主机 `/home/ubuntu/xhs-monitor/`（build context）+ 容器 `/app/`。
只传容器 → 下次 `docker build` 会被旧文件覆盖；只传宿主机 → 运行中的还是旧代码。

**校验一致性**（推荐每次部署后跑）：

```bash
sudo -n docker exec xhs-monitor sh -c "cd /app && md5sum *.py" > /tmp/a.txt
sudo -n bash -c "cd /home/ubuntu/xhs-monitor && md5sum *.py" > /tmp/b.txt
diff /tmp/a.txt /tmp/b.txt && echo 一致
```

### 常见报错

| 现象 | 含义 | 处理 |
|---|---|---|
| `-100 请登录账号` | 设备登录态失效 | 重新登录该设备 |
| `-100 登录已过期` | session 过期 | 重新登录 |
| `461` + `code=0` | 纯限流 | 停 6 分钟以上，别硬打 |
| `461` + `300011` | 账号层异常 | 换设备（换 IP 无效，>48h） |
| `300011` | mua 校验不过 | 检查材料是否自洽（见第二节警告） |
| `406` 空 | 无会话 | 设备未登录 / sid 失效 |

## 六、代理覆盖范围（2026-10-26 实测）

设备 `payload.proxy` 非空时，**整个小红书链路都走它**，实测逐链路确认（记账代理记账法）：

| 链路 | 是否走设备代理 |
|---|---|
| `check_device` / `fetch_notes_page` / `fetch_user_info` / `fetch_all_followings` / `fetch_note_share_link` | ✅ 全部 |
| 登录链：`send_code` / `submit` / `captcha` / `devices/{id}/check` | ✅ 全部 |
| 9.19.2 存量轨（`XhsSigner`） | ✅ |
| 设备生成：`generate_offline` 取 hmac 的 homefeed 请求 | ✅ |
| 代理测试接口 `/api/proxy/test` | ✅（显式指定，与被测代理本身无关） |
| `_get_direct_ip`（取「直连 IP」做对照） | ❌ 故意直连 |
| `notifier` 推送（企业微信/钉钉/飞书/Server酱/PushPlus） | ❌ 直连（与小红书无关，独立于设备） |
| `covers.download_cover` | ❌ 直连（**当前无调用方**，属死代码） |

**两条关键保证**

1. **代理不通 = 直接失败，绝不静默回落直连。**
   实测三种坏代理（不通端口 / socks5 不通 / 超时黑洞 IP）：`check_device` 返回
   `网络失败: … dial tcp 127.0.0.1:1 …`，`generate_offline` 抛
   `经代理 <p> 请求 homefeed 失败（代理可能不通）`。没有一条会「绕过代理偷偷直连」。
2. **取直连 IP 时不受环境变量影响。**
   `_http_get_ip_text` 用 `requests.Session(trust_env=False)`；
   否则服务器上一旦有 `HTTP_PROXY`/`HTTPS_PROXY`，「直连 IP」其实是环境代理出口，
   `ip_changed` 对照就失真（2026-10-26 修复）。

**出口 IP 探测端点**（2026-10-26 收敛为两个来源）：

| 角色 | 端点 | 返回格式 |
|---|---|---|
| 主 | `http://ip.3322.net` | 纯文本 IP |
| 主（同服务备用域名） | `http://members.3322.org/dyndns/getip` | 纯文本 IP |
| 备 | `https://only.nstool.netease.com/info.js` | JS 变量：`var ip = '1.2.3.4'; var dns = '…'; …`（GBK 页面） |

解析统一走 `_extract_ip()`：先按端点声明格式取（`js:ip` / `json:key`），失败再退「正文第一个 IPv4」。
原来的 `ifconfig.me` / `httpbin.org` / `api.ipify.org` 已按老板要求删除。

**复验方法**（改完任何网络相关代码都跑一遍）：

```bash
python tools/proxy_route_audit.py
# 起本地记账代理 → 把设备指向它 → 逐链路触发 → 检查每条是否真的经过代理
# 期望：15/15 条符合预期
```

## 七、已知隐患

1. ~~`xhs_core.py` 的算法库默认路径是 Windows 本地路径~~ → **2026-10-26 已修**

   现在两个签名核心都是「先读环境变量，没设就按本文件位置回落项目内 `vendor_algo/`」：

   ```python
   BASE = os.environ.get('XHS_ALGO_BASE') or os.path.join(
       os.path.dirname(os.path.abspath(__file__)), 'vendor_algo')
   ```

   含义：**零配置即可启动**；容器的 `XHS_ALGO_BASE=/app/vendor_algo` 仍然有效（等价）。
   资产缺失时报错会打出实际查找路径与当前 BASE，不再是裸 `FileNotFoundError`。
   9.49.1 的 SIG 矩阵还做了延迟加载 —— 只用 9.19.2 设备的部署不会因为缺 9491 资产而启动失败。

2. **`xhs_core` 内部有 `os.chdir(BASE)`**

   加载 9.19.2 的签名资产时会切一次工作目录（`_load_xhs_signer()`，仅在 import 时执行一次，
   之后立即还原）。目前所有运行期路径都是绝对路径（`DATA_DIR` / `DB_PATH` 来自 config），
   所以没出问题；以后写新代码**不要用相对路径读文件**。

## 八、红线

1. **不改生产代码做实验**。要试就在本地或 `/tmp` 沙箱。
2. **不重建镜像**做代码更新——`docker build` 会重装依赖，把环境搞漂。
3. **前端改动必须先验 JS 语法**（`node --check`）+ 浏览器实测，否则整页白屏。
4. **一次只改一件事**，改完验证再动下一件。
5. 材料版本相关常量改完，一定跑一遍签名自检（17 头 / sig 64 / 无 s1 / UA 9.49.1）。
